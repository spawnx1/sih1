1 · The problem & the big idea

Field Guide

When someone is scammed, the fraudster instantly moves the money through a chain of "mule" bank accounts and pulls it out as cash at an ATM — usually within minutes. Once it's cash, it's gone. This system takes a fraud complaint, traces where the money went, and forecasts, for each account still holding stolen funds: will it be cashed out, when, how, and roughly where.

"We don't just detect fraud after the fact — we forecast the cash-out, so police can freeze the account in time, and when they can't, we tell them which area to watch."

Why a forecast, not a report

The money reaches an ATM in minutes, but the average complaint is filed ~110 minutes after the fraud. So the winning move is not "catch them at the ATM" — it's "freeze the account before the ATM." Freezing takes seconds; a dispatch takes tens of minutes. The whole system optimises for a fast, well-justified freeze, with a geographic fallback for when freezing fails.

The honest reality

In ~66% of complaints the money was already cashed out before the complaint was even filed. We are useful in the cases where action is still possible — and we use that number to argue for the real fixes: faster reporting and proactive freezing.

2 · How it works — the five steps

Field Guide

A complaint names one victim and one disputed "seed" transaction. A time-respecting breadth-first walk (graphx/trail.py) reconstructs where the money went, attributing "taint" proportionally through each split and flagging accounts that are still holding stolen funds — the freeze targets. For each target, three models forecast the cash-out. Plain rules turn that into an action. An alert routes to the covering police station.

3 · The money trail & the graph signal

Field Guide

Before any model runs, the system reconstructs where the stolen money went. This is done fresh for every prediction — there is no giant precomputed graph, because that would leak the future.

A time-respecting breadth-first walk follows only edges timestamped before the as-of moment, ignores dust (<5% of the seed), attributes "taint" proportionally through each split, and stops at 4 hops or a cash-out. On top of the trail, nine graph features capture where an account sits in the fraud structure — the signal you cannot get from its own transactions alone.

Graph featureReads
hop_from_victimhow deep in the laundering chain
in/out_deg_1hfan-in and fan-out in the last hour
dispersion / flow_concentrationhow widely money spreads; how concentrated inflows are
ring_size / ring_prior_cashout_ratethe co-operating ring and its history
n_tainted_predecessorshow many upstream accounts carry stolen money
mule_scorea logistic "how mule-like" over features 1–8

4 · The three models

Field Guide

Three questions asked about one account that just received stolen money:

M1 — will it be cashed out, and when?

A discrete-time hazard model scored at 10, 20, 30, 45, 60 minutes, stitched into a rising cumulative "hazard curve." From it we read the action window (steepest-rise interval) and a severity: imminent / soon / later / unlikely. The 10-minute probability drives the decision.

M2 — how will the money leave?

Four classes: ATM, POS, onward_transfer, dormant. The last two stop police rushing an ATM when the money is about to move again or is going nowhere.

M3 — where? (and the part we're proudest of)

M3 ranks candidate ATMs, but only commits to the precision it can defend:

R5 — hierarchical abstention

If the top ATM's probability ≥ 0.22 and entropy ≤ 2.60 → name a terminal (top-5 ATMs). Else if the top cell ≥ 0.30 → name a ~5 km² cell and record it abstained. Else → name only the district. The output always says why it abstained. The system knows what it doesn't know.

Candidates set the ceiling

M3 only ranks a shortlist of ATMs, built from five sources: the account's own past ATMs (C1), ATMs near its withdrawal centroid (C2) and its KYC PIN (C3), its ring co-members' ATMs (C4 — the differentiator), and the district's top fraud ATMs (C5). Recall@50 = 0.82 — the hard ceiling on location accuracy.

5 · The six honesty rules

Field Guide

This is what makes the project credible. Six rules keep the science honest, and each is enforced by machinery — not by trust.

RuleForbidsEnforced by
R1 as-ofusing data from after the prediction momentevery feature reads only ts<as_of; the leakage test rebuilds a truncated corpus and asserts identical features
R2 label prefixa label reaching a modeldrop_leaky_columns strips all label_*
R3 no live locationa suspect's real-time GPSonly KYC centroid + historical footprint; true home coords never shipped
R4 honest metricssuspiciously high scorestarget 0.86–0.92; audit any single feature scoring >0.85 alone
R5 abstentionnaming a place on a flat distributiondistrict→cell→terminal gates in M3
R6 naive ISTtimezone bugsnaive IST internally; +05:30 only at JSON output

The one-line pitch

"We don't ask you to trust that we didn't cheat — we wrote tests that fail the build if we did, and they run on every change."

Why R4 is backwards on purpose

Most teams chase the highest accuracy. We capped ours at 86–92% and treat a single feature scoring above 0.85 as a leak to hunt. In this domain, a too-good number almost always means the model peeked at the answer.

6 · The data

Field Guide

Every row is synthetic, generated by gen/. This is a legal necessity — real money-mule records are personal financial data protected under the DPDP Act 2023 and cannot go into an open prototype — and, done right, a strength.

The world

8,000 accounts (~6% mules in rings of 3), ~250,000 transactions, 600 complaints, ~700 ATMs across four Pune districts (Pune City, Pimpri-Chinchwad, Hinjawadi, Hadapsar), indexed with H3 hexagons (res-7 ≈ 5 km² cells). The generator is deliberately hard: mules and honest customers overlap heavily (six legitimate archetypes that look mule-like), some edges are unobserved, and labels carry noise — so the model learns real behaviour, not a watermark.

The sealed corpus — the anti-cheating proof

The model is also tested on a deliberately different distribution it never trained on (different hotspots, slower forwarding, rarer fraud, a fraud type absent from training). Accuracy barely drops — 0.913 → 0.879. A memoriser would collapse; ours generalises.

9 · Decision, alerts & the API

Field Guide

The models produce probabilities; plain, readable rules — deliberately not another model — turn them into an action an officer can audit.

TierRuleAction
REDp_10m ≥ 0.60 AND tainted ≥ ₹5,000FREEZE now + alert
AMBER0.30 ≤ p_10m < 0.60watch / email brief
GREYbelow AMBERkeep tracing

Every recommendation carries a plain-English reason (the rule trace). Alerts route by district to the covering cyber police station (SHO), de-duplicated to one per account per 15 minutes. Alerts are simulated — payloads are built and logged, not actually sent.

10 · The console

Field Guide

One HTML file, no build step, three views. A calm, mature command-console look (muted steel-teal, red = act, amber = watch).

  • Command Centre — the overview: cases tracked, freeze-now count, money at risk, window left, metro risk map, and the urgency-sorted case queue.
  • Case view — one case: the live money-flow map, the ranked target-ATM menu, the hazard/channel/location forecast, the freeze recommendation, and the cinematic replay.
  • Case Centre — SOAR-style ticket lifecycle: priority, status, assignee, notes, resolution, audit trail, printable report and CSV export (backed by SQLite).

The live money-flow map

Leaflet with a dark Esri base + labels. Nodes are clean circular icons (victim, mules, ranked ATMs). Money is drawn as animated "waypoint" lines — gold for observed flow (victim→mules), red for the predicted routes (holding mule→each ATM). The lines are drawn in a screen-space SVG overlay glued to the map's pixel coordinates and trimmed to each circle's edge, so they stay pixel-perfect through zoom/pan and never bury the icons.

The best demo moment

Press Replay simulation: the case re-runs in fast motion inside a cinematic frame with a timecode and act labels. The gold flow traces first; the red target routes reveal at the cash-out climax — turning a probability into a visible, tense story.

11 · Run it & demo it

Field Guide

From zero

python -m venv .venv && .venv\Scripts\activate
pip install pandas numpy scikit-learn xgboost networkx \
            fastapi uvicorn pydantic pyarrow h3 matplotlib pytest

python -m gen.atms && python -m gen.generator          # build data
python -m gen.generator --sealed                        # sealed test set
python -m ml.train && python -m ml.evaluate             # train + evaluate
python -m pytest tests/ -q                              # leakage suite must pass

python demo.py                                          # headless story
python -m uvicorn api.main:app --port 8000              # open http://localhost:8000

Or: make all && make test && make demo && make api.

The 3-minute demo

  1. Open the console → "officer's screen; queue sorted by urgency."
  2. Click the top RED case → "traced to this account, holding ₹X."
  3. Hazard curve → "high chance of cash-out in ten minutes."
  4. Map + location → "this neighbourhood — and it abstains from naming one ATM. Honest AI."
  5. Recommendation → "action is FREEZE, alert routes to this station."
  6. Replay → "watch the money move and the risk rise."
  7. Close → "91% vs 50% for rules — and it tells us when it doesn't know."

Safety net

If the browser dies on stage, python demo.py prints the whole story to the terminal.

Not evidence
